Use **Authorization Code + PKCE with `S256`**, generate a fresh `state` and verifier per login attempt, and redeem the returned code only once.

## The flow

```text
Browser/app → Authorization server: authorization request + code_challenge + state
Authorization server → Browser/app: redirect_uri?code=...&state=...
Browser/app → Token endpoint: code + original code_verifier
Token endpoint → Browser/app: access token (and optional ID/refresh token)
```

PKCE makes a stolen authorization code insufficient: only the client that retained the original `code_verifier` can exchange it for tokens. [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636)

## Implement it

### 1. Register the client safely

1. Register exact redirect URI(s), such as `https://app.example.com/oauth/callback`.
   - Do not accept arbitrary or wildcard redirect URIs.
   - Use HTTPS (except permitted loopback development/native cases).

2. Use the provider’s published authorization and token endpoints, ideally through trusted OpenID Connect discovery.

3. Treat SPAs and native apps as **public clients**:
   - They cannot keep a `client_secret`.
   - Never put a client secret in browser or mobile-app code.

4. If this is OpenID Connect login, request `openid` scope and use a `nonce`.

5. Request only required scopes, for example `openid profile email`—not broad scopes “just in case.”

### 2. Start authorization

Generate and temporarily store these values for one login transaction:

- `state`: cryptographically random, opaque CSRF correlation value.
- `code_verifier`: random 43–128-character URL-safe string.
- `code_challenge`: `base64url(SHA-256(ASCII(code_verifier)))`, **without `=` padding**.
- `nonce`: random value, if using OpenID Connect.

`code_verifier` must be high entropy; RFC 7636 recommends generating 32 random bytes and base64url-encoding them. Always use `S256`, never `plain`. [RFC 7636 §4](https://www.rfc-editor.org/rfc/rfc7636#section-4)

Browser JavaScript example:

```js
function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, "-")
    .replace(/\//g, "_")
    .replace(/=+$/, "");
}

function randomUrlSafe(bytes = 32) {
  const value = new Uint8Array(bytes);
  crypto.getRandomValues(value);
  return base64url(value);
}

async function pkceChallenge(verifier) {
  const data = new TextEncoder().encode(verifier);
  const digest = await crypto.subtle.digest("SHA-256", data);
  return base64url(new Uint8Array(digest));
}

async function beginLogin() {
  const state = randomUrlSafe();
  const nonce = randomUrlSafe();          // OIDC only
  const codeVerifier = randomUrlSafe();
  const codeChallenge = await pkceChallenge(codeVerifier);

  // Prefer server-side/session storage where applicable.
  sessionStorage.setItem("oauth_txn", JSON.stringify({
    state, nonce, codeVerifier,
    createdAt: Date.now()
  }));

  const authUrl = new URL("https://issuer.example.com/authorize");
  authUrl.search = new URLSearchParams({
    response_type: "code",
    client_id: "YOUR_CLIENT_ID",
    redirect_uri: "https://app.example.com/oauth/callback",
    scope: "openid profile email",
    state,
    nonce,
    code_challenge: codeChallenge,
    code_challenge_method: "S256"
  });

  location.assign(authUrl);
}
```

The authorization request sends the **challenge**, not the verifier.

### 3. Process the callback before doing anything else

1. Parse `code`, `state`, `error`, and `error_description`.
2. Reject the callback if expected parameters are duplicated or malformed.
3. If `error` exists, stop and show a safe error; don’t try token exchange.
4. Load the stored transaction and compare `state` using a strict comparison.
5. Reject if state is missing, different, expired, or already used.
6. Delete/consume the transaction before or during the exchange to prevent replay.

```js
async function handleCallback() {
  const params = new URLSearchParams(location.search);

  const code = params.get("code");
  const returnedState = params.get("state");
  const stored = JSON.parse(sessionStorage.getItem("oauth_txn") || "null");

  if (!code || !stored || !returnedState ||
      returnedState !== stored.state ||
      Date.now() - stored.createdAt > 10 * 60_000) {
    throw new Error("Invalid or expired OAuth callback");
  }

  sessionStorage.removeItem("oauth_txn"); // one-time use

  return exchangeCode(code, stored.codeVerifier);
}
```

`state` protects the authorization response from being accepted in the wrong browser session; PKCE does not replace it. OAuth’s current security guidance requires clients to use PKCE and maintain strong redirect-URI protections. [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700)

### 4. Exchange the code at the token endpoint

Send a form-encoded POST over HTTPS:

```js
async function exchangeCode(code, codeVerifier) {
  const response = await fetch("https://issuer.example.com/oauth/token", {
    method: "POST",
    headers: { "Content-Type": "application/x-www-form-urlencoded" },
    body: new URLSearchParams({
      grant_type: "authorization_code",
      client_id: "YOUR_CLIENT_ID",
      code,
      redirect_uri: "https://app.example.com/oauth/callback",
      code_verifier: codeVerifier
    })
  });

  if (!response.ok) {
    throw new Error(`Token exchange failed: ${await response.text()}`);
  }
  return response.json();
}
```

For a confidential server-side web client, authenticate the client at this endpoint using the provider’s prescribed method (often HTTP Basic or private-key JWT). Still use PKCE. Do not send a secret in a browser or native application.

The authorization server recomputes the challenge from `code_verifier`; a mismatch must fail with `invalid_grant`. [RFC 7636 §4.6](https://www.rfc-editor.org/rfc/rfc7636#section-4.6)

### 5. Validate and store tokens appropriately

- **Access token:** send only to the intended resource server; treat it as a bearer credential.
- **ID token (OIDC):** validate signature, issuer, audience/client ID, expiry, and `nonce`. Do not merely decode it and trust its JSON.
- **Refresh token:** store only where the platform can protect it.
  - Best web architecture: backend-for-frontend keeps refresh/access tokens server-side in a session.
  - Browser-only SPA: avoid persistent `localStorage` for long-lived tokens if possible; XSS can steal them.
- Clear tokens/session on logout; support refresh-token rotation if the provider offers it.

## Security checklist

- [ ] `S256`, never `plain`
- [ ] New verifier, state, and OIDC nonce for every attempt
- [ ] Cryptographic randomness (`crypto.getRandomValues`, not `Math.random`)
- [ ] Exact, pre-registered redirect URI; same URI in token exchange
- [ ] State checked before accepting the code
- [ ] Authorization code and local transaction consumed once
- [ ] HTTPS for authorization, callback, and token endpoint
- [ ] No client secret in SPA/native code
- [ ] Validate ID tokens; do not trust decoded claims alone
- [ ] Avoid logging query strings, codes, verifiers, or tokens
- [ ] Use short code/transaction expiry and restrictive scopes
